# EDITOR_research.md — A Faster-than-Blender 3D Editor & Mesh-Editing Core in Rust

> **Purpose.** The same playbook as [`GUI_research.md`](GUI_research.md), aimed at a
> bigger target: survey the best 3D editors and mesh-editing engines, find *where
> they are slow and why*, prove the alternative at the instruction level
> (reproducer in [`docs/editor_research/asm/`](docs/editor_research/asm/)), and
> design a fully-featured editor — with best-in-class **mesh editing** — grounded
> in what `dumpster_fire_engine` already has.
>
> **Thesis.** Blender is the feature bar to clear, but its *edit-mode performance*
> is a known, documented weakness: main-thread transforms, full draw-batch
> rebuilds per edit, single-threaded selection that crawls past ~20M polys, and a
> pointer-chasing BMesh whose sculpt path (DynTopo) spends ~30% of its time
> fetching memory once the mesh fragments. A **data-oriented, SoA, arena-backed,
> rayon+GPU-parallel** core — decoupled from rendering and updated incrementally —
> can beat it on the metrics that make modeling feel slow, while matching its
> toolset. This engine is unusually well-positioned: its meshes are *already*
> struct-of-arrays, it already has a GPU compute-dispatch system, generational
> arenas, and a rayon pool.
>
> **Reproducibility.** Every assembly listing here is regenerated by
> `bash docs/editor_research/asm/generate.sh` (local `rustc 1.94.1`,
> `-O -C opt-level=3 -C target-cpu=x86-64-v3`, Intel syntax) and reproduces on
> Compiler Explorer `r1940` (rustc 1.94.0) — the toolchain equivalence was verified
> byte-for-byte in the GUI study.

## 1. Executive summary

**Where Blender hurts (sourced, §3.1):**
- Edit-mode vertex transforms on dense meshes are slow from *depsgraph + mesh
  update + batch-creation* overhead, not the math.
- Selection "gets really slow" past ~20M polys / 10k objects — effectively
  single-threaded.
- Sculpt mode is fast *because it bypasses edit-mode's draw path entirely*;
  edit-mode drawing is itself the bottleneck.
- DynTopo is "highly cache bound; upwards of 30% of time… fetching memory" due to
  fragmentation of its pointer-linked BMesh.
- Three different data structures / undo stacks / draw paths (FACES, GRIDS, BMESH)
  for sculpt alone — architectural drag.

**The counter, proven in §5:**
| Lever | Evidence (asm) |
|---|---|
| SoA vertex streams transform in wide SIMD | `translate_soa` → 15 `vaddps`; `affine_row_soa` → 43 FMA/mul/add |
| Index-based half-edge in dense arrays beats pointer-chasing | pointer one-ring = 3 dependent loads to random addresses/step; SoA = prefetchable indexed loads |
| Normal recompute streams instead of gathers | `face_normals_soa` 12 packed `vmovups` vs indexed 16 scalar gathers |
| Selection is branchless & vectorized | `box_select_soa` 5 `vcmpps`; `count_selected` 12 packed |
| Subdivision averaging vectorizes (and ports to GPU compute) | `quad_face_points` 12 packed `vaddps/vmulps` |
| Incremental dirty-range upload, not full rebuild | `upload_dirty_range` = one `memcpy` of the touched span |

**The engine fit (§2):** meshes are already `VertexStreams` SoA
(`crates/forge_gltf/src/mesh.rs`); there's a GPU compute system
(`Ore`/`Forge`/`ForgeMaster`, `src/forge_master/`) that already runs
`morph_blend`/`skin_palette`/`instance_transforms` compute shaders — the exact
substrate for GPU subdivision/sculpt/normal-recompute; generational `Arena`/`Handle`
(`src/resource_manager/manager.rs`) for stable element identity; and a rayon pool.

**What we must build (§8):** an editable topology layer (SoA index-based
half-edge), a spatial BVH (for ray-triangle picking/selection), a transaction-based
undo system, a modal tool framework + selection modes in the editor, GPU-compute
mesh kernels, and serialization. The redesign reuses the SoA streams, the compute
dispatch, the arenas, and the editor's existing viewport/gizmo (now extended in
`src/bin/editor.rs`).

## 2. Baseline

`dumpster_fire_engine` today is a **renderer + scene editor**, not a modeler.

**Reusable foundations**
- **Mesh is already SoA.** `forge_gltf::mesh::VertexStreams`
  (`crates/forge_gltf/src/mesh.rs`): parallel `positions: ThinVec<[f32;3]>`,
  `normals`, `tangents`, `uv_sets`, `colors`, `joints`, `weights`. `Primitive` adds
  `indices`, `bounds: Aabb`, `morph_targets`. This is the *right* layout for fast
  editing (§5) — most engines have to retrofit it.
- **GPU vertex** `ForgeVertex` (48 B: pos+normal+tangent+uv), `MeshOre`, `GpuMesh`
  (`src/forge_master/ore.rs`) with dedicated-transfer-queue upload and BDA for BLAS.
- **GPU compute dispatch.** `OreKind`/`Ore`/`Forge`/`ForgeMaster`
  (`src/forge_master/{ore,forge,master}.rs`) + `ComputeDispatchGraph`
  (`src/render/compute_dispatch.rs`); GLSL→SPIR-V via `build.rs`. Existing compute
  shaders: `morph_blend`, `skin_palette`, `instance_transforms`, `splat_sort`.
- **Generational arenas** `Arena<Tag, T>`/`Handle` (`src/resource_manager/manager.rs`)
  — type-tagged, generation-checked: ideal for vertex/edge/face/half-edge handles.
- **Math/pick** glam, `Aabb`, ray-AABB picking + `mikktspace` tangents.
- **Editor** (`src/bin/editor.rs`): 4-quadrant viewport grid, actor selection,
  TRS gizmo (+ snapping/duplicate/frame/stats just added), spawn, panels.
- **rayon** pool (used for asset loading; ready for mesh ops).

**Gaps to fill**
- No editable topology (no half-edge/adjacency) — meshes are immutable triangle
  soup after upload.
- No spatial index (BVH/octree) → only actor-level ray-AABB picking, no
  ray-triangle, no vertex/edge/face picking.
- No undo/command/transaction system; no scene serialization.
- No modeling tools, selection modes, modifiers, UV/sculpt/retopo.

## 3. Cross-tool survey

### 3.1 Blender — the feature bar, and its perf ceiling
**BMesh** is an edit-mode structure built on *double-linked circular lists* (a
radial-edge / half-edge relative); crucially the **disk cycle is independent of face
data**, so wire edges and **non-manifold** geometry are first-class — and it stores
**per-element flag bitfields** (selection/visibility). It deliberately uses a
**struct-of-arrays paradigm** "to decrease the amount of memory accessed in hot
loops" ([BMesh design](https://developer.blender.org/docs/features/objects/mesh/bmesh/)).
**But** the documented pain (sourced):
- Edit-mode transform slow from depsgraph/mesh-update/batch overhead
  ([T57936](https://developer.blender.org/T57936),
  [devtalk](https://devtalk.blender.org/t/why-is-it-so-hard-to-make-editting-high-poly-meshes-more-responsive/6744)).
- Selection crawls >20M polys; sculpt is fast only by avoiding edit-mode's draw
  path ([blenderartists](https://blenderartists.org/t/disappointed-in-blenders-edit-mode-performance/636048)).
- **DynTopo cache-bound, ~30% in memory fetch** from fragmentation; sculpt splits
  across **3 data structures/undo/draw paths** (FACES/GRIDS/BMESH)
  ([code.blender.org sculpt status](https://code.blender.org/2019/06/sculpt-mode-features-branch-status-report/)).
**Steal:** SoA hot loops, per-element flags, non-manifold support, disk-cycle idea.
**Beat:** kill pointer-chasing (index arrays), kill per-edit batch rebuild
(incremental upload), parallelize selection/transform (rayon+SIMD), unify the
data/undo/draw path.

### 3.2 Maya + OpenSubdiv — GPU subdivision is solved
Pixar's **OpenSubdiv** does Catmull-Clark splitting/averaging in a **single compute
kernel**, "3 ms" for a 30k-poly char to L2 where Maya took "100 ms"; adaptive mode
emits **Bézier/Gregory patches** tessellated on GPU (max valence ~27)
([OpenSubdiv architecture](https://graphics.pixar.com/opensubdiv/architecture.html)).
Recent **edge-friend** work gives deterministic GPU Catmull-Clark without atomic FP
([CGF 2023](https://onlinelibrary.wiley.com/doi/full/10.1111/cgf.14863)).
**Steal:** uniform-averaging kernel (it's just the averaging in §5 exp5, ported to a
compute shader on our `Ore`/`Forge` system), feature-adaptive patches for the render
path.

### 3.3 ZBrush / Mudbox — sculpting at scale
ZBrush sculpts hundreds of millions of polys via a tiled/streamed representation and
a sculpting-specific data path (not a general half-edge). **Lesson:** sculpt wants a
**separate, contiguous, GPU-resident** representation + a **PBVH-style spatial split**
for brush locality — not the topology editor's structure. Match Blender's split but
*share one undo journal and one draw path*.

### 3.4 Unreal — the tool-framework model
Unreal's **Interactive Tools Framework** (modeling mode, GeometryProcessing) exposes
`IToolsContext{Queries,Transactions,Render,Asset}` APIs and an in-viewport gizmo
system; tools are modal objects that emit transactions
([ITF](http://www.gradientspace.com/tutorials/2021/01/19/the-interactive-tools-framework-in-ue426)).
Nanite shows the value of decoupling *authoring* topology from *render* topology.
**Steal:** the **ToolsContext + transaction** boundary — every tool change is a
reversible transaction; the editor owns selection/render/asset APIs the tools call.

### 3.5 Godot — pragmatic editor plumbing
`EditorPlugin`s register viewports/docks/**gizmo plugins** and integrate with a
high-level **`UndoRedo`** "actions" API (method + property changes batched into a
reversible action) ([Godot UndoRedo](https://docs.godotengine.org/en/stable/classes/class_undoredo.html),
[editor plugins](https://deepwiki.com/godotengine/godot/9-editor-plugins)).
**Steal:** the action/transaction granularity and plugin registration shape.

### 3.6 Rust ecosystem — what we can lean on
`glam` (have it), `mikktspace` (have it). For topology, OpenMesh/`half_edge`-style
designs and `baby_shark` (Rust mesh processing: half-edge, decimation, boolean) show
viable Rust half-edge designs; `parry`/BVH crates show ray-triangle acceleration.
**Lesson:** an **index-based half-edge in `Vec`s/arenas** is the idiomatic, fast Rust
choice (no `Rc`/pointer graph) — and matches our arena pattern.

### 3.7 Comparison matrix
| Tool | Topology core | Subdivision | Sculpt | Parallelism | Undo | Weakness we beat |
|---|---|---|---|---|---|---|
| Blender | BMesh (linked lists, SoA-ish) | CPU (modifier) | DynTopo/Multires (3 paths) | mostly single-thread | per-mode stacks | edit-mode perf, fragmentation, batch rebuild |
| Maya | half-edge-ish | **OpenSubdiv GPU** | — | partial | command engine | closed, heavy |
| ZBrush | sculpt-specific | — | **billions** | yes | sculpt history | not a general editor |
| Unreal | GeometryProcessing | patches | partial | task graph | **ITF transactions** | C++, heavyweight |
| Godot | SurfaceTool/ArrayMesh | limited | limited | limited | **UndoRedo actions** | weak modeling |
| **this engine (target)** | **SoA index half-edge in arenas** | **GPU compute (Ore/Forge)** | **GPU PBVH** | **rayon + GPU** | **delta-journal transactions** | — |

## 4. Mesh data structure — how to beat BMesh

Design: a **struct-of-arrays, index-based half-edge** stored in generational arenas,
keeping editable topology separate from the GPU render buffers.

```
HalfEdgeMesh {                         // all arenas are dense Vec<_> + free list
    // half-edge arrays (SoA — parallel, indexed by HeId: u32)
    he_next:  Vec<u32>,   // next around the face loop
    he_twin:  Vec<u32>,   // opposite half-edge (INVALID for boundary)
    he_vert:  Vec<u32>,   // origin vertex
    he_face:  Vec<u32>,   // owning face (INVALID for boundary loop)
    // element tables
    vert_he:  Vec<u32>,   // one outgoing half-edge per vertex
    face_he:  Vec<u32>,   // one half-edge per face
    // attribute layers (SoA, parallel to vertices) — Blender-style custom layers
    pos: Vec<[f32;3]>, nrm: Vec<[f32;3]>, uv: Vec<[f32;2]>, … ,
    // per-element flag bitfields (selection/visibility/crease)  — BMesh-style
    vflag: Vec<u8>, eflag: Vec<u8>, fflag: Vec<u8>,
    free_he/free_vert/free_face: Vec<u32>,   // stable ids, no compaction churn
}
```

**Why this beats BMesh on the documented pain points:**
1. **No pointer chasing.** Adjacency is `u32` indices into dense arrays →
   prefetchable, cache-resident; §5 exp1 shows the pointer version is 3 dependent
   loads to random addresses per ring step (the DynTopo memory-fetch tax), while the
   index version streams from dense arrays.
2. **No fragmentation.** Stable ids + free lists mean split/collapse reuse slots
   in place (Blender had to add an in-place rewrite + defragmenting allocator to
   claw back 10–30%); we get locality by construction.
3. **Editing never touches the GPU layout.** Topology edits mutate the SoA arrays;
   a separate pass emits/uploads only the **dirty range** of `ForgeVertex` (§5 exp4),
   instead of Blender's full per-edit batch rebuild.
4. **Non-manifold & wire edges** kept (disk-cycle idea): `he_twin = INVALID` on
   boundaries; a vertex's edges are walkable without faces.
5. **Attribute layers** (extra UV/color/crease/skin) are just more SoA arrays —
   `O(1)` to add, vectorizable to process.

Sculpt uses a **separate** contiguous buffer + GPU **PBVH** (spatial split for brush
locality), but shares one **transaction journal** and one render path (fixing
Blender's 3-path split).

## 5. Assembly deep-dives

Snippets in [`docs/editor_research/asm/`](docs/editor_research/asm/); regenerate with
`generate.sh`. Flags: `rustc -O -C opt-level=3 -C target-cpu=x86-64-v3`, Intel syntax.

### 5.1 Half-edge traversal: index-SoA vs pointer-AoS (`exp1_halfedge.rs`)
The BMesh-style pointer ring is small but **latency-bound** — every step is a chain
of dependent loads to wherever the allocator put the node:
```asm
one_ring_sum_ptr:                ; .LBB0_2 loop body:
        mov  rcx, qword ptr [rcx + 8]    ; load ->twin   (random address)
        mov  eax, dword ptr [rcx + 16]   ; load ->vert   (depends on twin)
        add  rax, rdx
        mov  rcx, qword ptr [rcx]        ; load ->next   (depends on twin)
        cmp  rcx, rdi ; jne .LBB0_2
```
Three serialized cache-miss-prone loads per neighbor — exactly Blender's "~30% time
fetching memory." The SoA version instead does **indexed loads from dense, contiguous
arrays** (`mov edx, [rcx + 4*rax]`, …) that the prefetcher and cache handle well, and
the arrays never fragment. *Same Big-O, vastly better constant + scalable to SIMD/GPU.*

### 5.2 Selection transform — the operation Blender stalls on (`exp2_transform.rs`)
The kernel is embarrassingly parallel; on SoA streams it vectorizes hard:
```asm
; translate_soa inner loop — packed adds, 8 floats/instr (15 vaddps total)
.LBB?:  vaddps  ymm0, ymm1, ymmword ptr [rax + 4*rcx]
        vmovups ymmword ptr [rax + 4*rcx], ymm0   ; … unrolled
```
`affine_row_soa` (the per-row kernel of `Mat4 * positions`) compiles to **43**
`vfmadd/vmulps/vaddps` — a pure FMA stream. So a gizmo move/scale over a selection is
SIMD throughput-bound, and trivially `rayon`-parallel across chunks — versus
Blender's main-thread depsgraph round-trip. (Sparse selection by index list,
`translate_selected_soa`, falls back to 18 scalar ops — motivating *contiguous*
selection compaction before a transform, or a GPU scatter.)

### 5.3 Normal recompute: stream vs gather (`exp3_normals.rs`)
`face_normals_indexed` (AoS `[f32;3]` + index buffer) issues **16 scalar `vmovss`
gathers** per the random index access; `face_normals_soa` (pre-gathered corner
streams) issues **12 packed `vmovups`** and packed cross-product mul/sub across many
faces. Recomputing normals after every edit — constant in modeling — wants the SoA
stream (and it ports straight to a compute shader).

### 5.4 Branchless selection (`exp4_select_upload.rs`)
`box_select_soa` lowers the 6-way AABB predicate to **5 `vcmpps`** + mask store (no
branches) → vectorizes and `rayon`-parallelizes; `count_selected` is **12 packed**
adds. This is the path Blender single-threads past 20M polys. And
`upload_dirty_range` is a single `copy_nonoverlapping` of the touched span — the
incremental-upload win over full batch rebuild.

### 5.5 Subdivision averaging (`exp5_subdiv.rs`)
`quad_face_points` and `edge_points` (Catmull-Clark face/edge rules) are pure
averaging over SoA streams → **12 packed `vaddps/vmulps`**. The identical arithmetic
is one GLSL compute kernel on our `Ore`/`Forge` system (OpenSubdiv's "single compute
kernel" shape), giving the 3 ms-class subdivision Maya needed 100 ms for.

## 6. Architecture for a blazing editor

1. **Decoupled edit ↔ render.** The half-edge SoA is the source of truth; a
   *bridge* emits `ForgeVertex` + indices and uploads **only dirty ranges** into a
   persistent, ring-buffered GPU mesh buffer (reuse the `RingBuffer`/upload pattern
   from `ui_render`). No per-edit rebuild.
2. **Parallel everywhere.** CPU ops fan out via `rayon` (selection, transform,
   normals, weld); heavy/regular ops (subdivision, sculpt brush, remesh, normal
   recompute at scale) dispatch as **compute Ores** through `ForgeMaster`.
3. **GPU subdivision** as new `OreKind::Subdivide` compute shaders (face/edge/vertex
   point passes), feeding an adaptive patch render path later.
4. **GPU sculpt + PBVH**: a spatial split over a contiguous sculpt buffer; brushes
   are compute dispatches touching only affected nodes; shared undo journal.
5. **Spatial index (BVH)** over triangles for ray-triangle picking, box/lasso
   selection, snapping, and brush hit-tests — built incrementally, refit on edit.
   (Foundation also reusable for the existing BLAS/RT path.)
6. **Transaction-based undo** (Unreal ITF / Godot UndoRedo): every tool emits a
   reversible **delta** (changed element ids + before/after attribute spans). Delta
   journaling — not full snapshots — keeps undo O(touched), matching the edit cost.
7. **Modal tool framework**: tools are closed-enum dispatched (no `Box<dyn>` on the
   hot path — same rule the GUI study proved in §4.1 of `GUI_research.md`), each
   implementing begin/update(drag)/commit against a `ToolContext` (selection, mesh,
   gizmo, transaction sink).
8. **Selection modes**: vertex/edge/face, with box/lasso/paint/loop/ring; selection
   stored as SoA flag arrays (§5.4) for parallel ops.

## 7. Full feature set (to match/exceed the DCC bar)

- **Modeling tools:** extrude, inset, bevel (vert/edge/face), loop cut & slide, knife,
  bridge, spin, merge/weld, dissolve, fill/grid-fill, symmetrize, separate/join.
- **Non-destructive modifier stack:** mirror, subdivision (GPU), solidify, array,
  boolean/CSG, decimate (quadric), remesh (voxel/quad), shrinkwrap, lattice.
- **Sculpt:** GPU PBVH, dynamic topology, multires; standard brush set; masking.
- **Retopology:** snap-to-surface, poly-build, auto-retopo hooks.
- **UV:** unwrap (LSCM/ABF), seams, pack, live preview.
- **Selection:** modes above + select-similar/linked/loops/rings, grow/shrink.
- **Precision:** grid/angle/increment snap (gizmo already supports it), vertex/edge/
  face snapping, numeric entry, pivots, custom orientations, symmetry.
- **Scene/asset:** multi-object edit, instancing, glTF import (have it) + **export**,
  native binary scene save/load, asset browser.
- **Editor UX:** the existing 4-quadrant viewport + panels, plus a mesh-edit mode,
  N-panel/inspector for element attributes, statistics overlay (added), measure.

## 8. Design proposal mapped to the engine

**New crate `crates/forge_mesh`** (peer of `forge_gltf`): the editable half-edge SoA
(§4), topology ops (extrude/bevel/loopcut/subdivide/weld/dissolve), `rayon`-parallel
kernels, BVH, and a glTF↔half-edge bridge (reuse `forge_gltf::VertexStreams`).

**Engine integration**
- `src/forge_master/ore.rs`: add compute `OreKind`s — `SubdivideFace/Edge/Vertex`,
  `RecomputeNormals`, `SculptBrush`, `BvhRefit` — with GLSL in `assets/shaders/`
  (compiled by `build.rs`, same as `morph_blend`).
- Mesh GPU residency: a persistent editable `GpuMesh` with **dirty-range upload**
  (extend `GpuMesh::upload`, mirror `ui_render::RingBuffer`).
- `src/resource_manager/`: a `MeshEditDoc` arena (handles for meshes/elements) + a
  `Transaction`/`History` module (the missing undo system) — delta journaling.
- Picking: extend `editor::pick_actor` (ray-AABB) to **ray-triangle via BVH** for
  vertex/edge/face hit-testing.

**Editor (`src/bin/editor.rs`)**
- Add an **Edit Mode** toggle per selected mesh; element selection modes
  (vert/edge/face); a modeling toolbar; reuse the TRS gizmo (with the snapping just
  added) for element transforms.
- Tools are modal `ToolContext` consumers emitting transactions; the existing
  immediate-mode UI (`ui_manager`) draws tool options/inspector.

**Reuse, don't reinvent:** SoA `VertexStreams`, `Arena`/`Handle`, `Ore`/`Forge`/
`ForgeMaster` compute, `rayon`, `mikktspace`, the viewport/gizmo/panels, and the
`RingBuffer` upload pattern.

## 9. Roadmap & how we measurably beat Blender

Each phase ships behind the engine's benchmark culture (add `benches/mesh_*`,
criterion + iai-callgrind) with explicit targets vs Blender.

| Phase | Deliverable | Bench / target |
|---|---|---|
| 0 | `forge_mesh` crate: SoA index half-edge + glTF bridge + validate/round-trip | build a 1M-tri half-edge < X ms; one-ring traversal ns/step vs pointer baseline |
| 1 | Selection (vert/edge/face) + SoA flag ops + box/lasso | **box-select 20M verts at interactive rates** (Blender's stated wall) |
| 2 | Transform of selection (rayon+SIMD) + dirty-range GPU upload | move 5M-vert selection at 60 fps; upload = O(touched), not O(mesh) |
| 3 | Core tools: extrude/inset/bevel/loopcut/dissolve/weld | op latency on 1M-tri mesh; undo O(touched) |
| 4 | BVH + ray-triangle picking; snapping | pick/hover latency on 20M tris |
| 5 | GPU subdivision (`Ore` compute) | **30k→L2 in single-digit ms** (OpenSubdiv-class, vs Maya 100 ms) |
| 6 | Normals/tangents recompute (GPU + rayon) | recompute 5M tris/frame |
| 7 | Sculpt: GPU PBVH + brushes + DynTopo | sustained stroke fps at 50M+; no fragmentation stall |
| 8 | Modifier stack, booleans/CSG, decimate/remesh, UV | correctness + perf suites |
| 9 | Transaction history, native save/load, glTF export | undo/redo latency; round-trip fidelity |

**The "beat Blender" scoreboard** is concrete and falsifiable: interactive 20M-poly
selection, O(touched) edits/undo, single-digit-ms subdivision, and no DynTopo
memory-fetch cliff — each backed by the kernels proven in §5 and the GPU compute path
the engine already runs.
